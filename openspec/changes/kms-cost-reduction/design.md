## Context

当前 security-enhancement 方案使用阿里云 KMS 管理敏感凭证，月费用约 ¥50-100。本项目为个人/小团队项目，成本敏感。

当前架构：
- 后端：阿里云函数计算 (FC) + FastAPI
- 数据库：阿里云 RDS PostgreSQL Serverless
- 存储：阿里云 OSS

约束条件：
- Serverless 架构，函数无状态
- 需保持与现有阿里云生态集成
- 安全等级不能降低（仍需 AES-256-GCM 加密）
- 密钥管理需要可靠备份机制

## Goals / Non-Goals

**Goals:**
- 将凭证管理成本从 ¥50-100/月 降至 ¥5-10/月
- 保持同等安全等级（AES-256-GCM 加密）
- 简化依赖，移除 KMS SDK
- 提供可靠的密钥备份和恢复机制

**Non-Goals:**
- 不改变其他安全方案（Token 存储、请求签名、LLM 脱敏）
- 不引入跨云服务（如 AWS Secrets Manager）
- 不自建 Vault 等复杂密钥管理系统
- 不降低安全等级（如使用明文或弱加密）

## Decisions

### 1. 密钥存储方案

**决策：OSS 服务端加密存储主密钥**

理由：
- OSS SSE-KMS 与 SSE-OSS 选项，但 SSE-KMS 仍依赖 KMS
- 使用 SSE-OSS（阿里云托管密钥），无额外费用
- 主密钥文件加密存储在 OSS，权限控制通过 RAM Policy

替代方案：
- KMS 托管密钥 → 拒绝：成本高
- 本地文件存储 → 拒绝：Serverless 无法持久化
- RAM Secret → 拒绝：功能有限，不适合复杂场景

实现方式：
```
存储：
1. 生成 256-bit 主密钥（随机）
2. 主密钥存储在 OSS bucket（启用 SSE-OSS 加密）
3. OSS bucket 通过 RAM Policy 限制仅 FC 角色访问

使用：
1. FC 启动时从 OSS 读取主密钥
2. 内存缓存主密钥（单次请求生命周期）
3. 使用主密钥进行信封加密
```

### 2. 信封加密方案

**决策：本地实现信封加密（Envelope Encryption）**

理由：
- 与 KMS GenerateDataKey 原理相同，但无需 KMS API 调用
- Python cryptography 库成熟可靠
- 每个凭证使用独立数据密钥，主密钥加密数据密钥

替代方案：
- 直接用主密钥加密 → 拄弃：安全性较低，无法单独轮换
- KMS 信封加密 → 拒绝：成本高

实现方式：
```
加密凭证：
1. 生成随机 256-bit 数据密钥
2. 用数据密钥 AES-256-GCM 加密凭证值
3. 用主密钥 AES-256-GCM 加密数据密钥
4. 存储：加密数据密钥 + 密文凭证 + IV + AuthTag

解密凭证：
1. 从存储读取加密数据密钥和密文
2. 用主密钥解密数据密钥
3. 用数据密钥解密凭证值
```

### 3. 密钥轮换方案

**决策：应用层定时轮换（90 天周期）**

理由：
- KMS 自动轮换需要付费
- 应用层轮换更灵活，可控成本
- 使用 FC 定时触发器执行轮换

实现方式：
```
1. FC 定时触发器每 30 天检查密钥年龄
2. 超过 90 天触发轮换：
   - 生成新主密钥
   - 用新主密钥重新加密所有数据密钥
   - 更新 OSS 中的主密钥文件
   - 保留旧主密钥备份 7 天（用于紧急恢复）
3. 记录轮换日志
```

### 4. 密钥备份方案

**决策：OSS 多副本 + 本地备份**

理由：
- OSS 自动提供多副本存储
- 本地备份用于灾难恢复（OSS 不可用时）
- 备份文件同样加密存储

实现方式：
```
自动备份：
- OSS bucket 启用跨区域复制（可选，额外费用）
- 主密钥文件版本控制（OSS 版本控制功能）

手动备份：
- 轮换时将旧密钥下载保存到本地安全存储
- 开发者保存一份离线备份（加密文件）
```

### 5. 凭证存储位置

**决策：OSS bucket + FC 环境变量**

理由：
- 加密凭证存储在 OSS bucket
- FC 环境变量存储 bucket 名称和路径引用
- 与 KMS 方案保持一致的部署流程

实现方式：
```
部署时：
1. Terraform 创建 OSS bucket（启用 SSE-OSS）
2. 生成主密钥并上传到 OSS
3. 加密所有凭证并上传到 OSS
4. FC 环境变量配置 OSS bucket 名称

运行时：
1. FC 启动从 OSS 读取主密钥和加密凭证
2. 解密凭证后内存缓存
3. 使用解密后的凭证连接数据库等
```

## Risks / Trade-offs

### Risk 1: 自管密钥安全性
→ **Mitigation**: OSS RAM Policy 严格限制访问权限，主密钥文件启用 SSE-OSS 加密，仅 FC 执行角色可读取

### Risk 2: 密钥丢失导致数据无法解密
→ **Mitigation**: OSS 版本控制保留历史版本，定期本地备份，轮换时保留旧密钥过渡期

### Risk 3: 密钥轮换失败
→ **Mitigation**: 轮换前验证所有凭证可正常解密，失败时保留旧密钥并告警

### Risk 4: OSS 不可用
→ **Mitigation**: FC 内存缓存解密后凭证，短时 OSS 故障不影响运行；长期故障使用本地备份恢复

### Trade-off: 自管密钥需更多运维关注
→ **Acceptance**: 成本节省值得付出额外运维努力；自动化轮换脚本降低运维负担

## Migration Plan

### Phase 1: 基础设施准备
1. Terraform 创建 OSS bucket（启用 SSE-OSS、版本控制）
2. 配置 RAM Policy 限制访问
3. 创建 FC 定时触发器（密钥轮换）

### Phase 2: 密钥和凭证迁移
1. 生成主密钥
2. 加密现有凭证（DB密码、微信Secret、LLM API Key）
3. 上传到 OSS bucket
4. 更新 FC 环境变量（移除明文凭证，配置 OSS 引用）

### Phase 3: 代码部署
1. 部署 secrets_service.py（本地加密服务）
2. 更新 config.py 从 OSS 读取凭证
3. 验证所有服务正常连接

### Rollback Strategy
- 保留原环境变量明文凭证备份（加密存储）
- 需要回退时恢复环境变量明文凭证
- OSS bucket 保留所有历史版本密钥
