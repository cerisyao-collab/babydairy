## Context

当前系统架构：
- **前端**: 微信小程序，使用 wx.storage 存储 JWT Token（明文）
- **后端**: 阿里云函数计算 (FC) + FastAPI
- **数据库**: 阿里云 RDS PostgreSQL Serverless（VPC 内网）
- **LLM**: 阿里云通义千问（DashScope API）

当前安全问题：
1. Token 明文存储在小程序本地存储，存在逆向工程和物理访问风险
2. 所有敏感凭证（DB密码、微信Secret、LLM API Key）以环境变量存储
3. 用户数据直接发送到 LLM，无脱敏处理
4. 数据库敏感字段明文存储
5. 无请求签名，存在重放攻击风险

约束条件：
- 微信小程序限制：无法使用原生加密库，依赖微信内置能力
- Serverless 架构：函数无状态，KMS 调用需考虑冷启动延迟
- 成本控制：KMS 和审计服务有额外费用

## Goals / Non-Goals

**Goals:**
- 凭证管理：所有敏感凭证通过 KMS 加密存储
- 传输安全：小程序请求防重放防篡改
- 存储安全：敏感字段加密存储
- 数据隐私：发送到 LLM 的数据脱敏处理
- 审计追踪：关键操作有日志记录

**Non-Goals:**
- 不实现端到端加密（超出当前需求）
- 不实现多因素认证（微信已有）
- 不实现数据备份加密（RDS 自动备份）
- 不实现安全合规认证（如等保）

## Decisions

### 1. 凭证管理方案

**决策：使用阿里云 KMS**

理由：
- 与现有阿里云生态集成良好
- 支持密钥自动轮换
- 调用审计内置
- 成本可控（约 ¥50-100/月）

替代方案：
- AWS Secrets Manager → 拒绝：跨云复杂度高
- 自建 Vault → 拒绝：运维成本高，Serverless 不友好
- 环境变量加密 → 拒绝：密钥管理仍需解决

实现方式：
```
部署时：Terraform 创建 KMS 密钥 → 加密凭证 → 存储密文到 FC 环境变量
运行时：FC 启动 → 调用 KMS Decrypt → 内存缓存明文凭证
```

### 2. 小程序 Token 存储方案

**决策：AES 加密存储 + 设备绑定**

理由：
- 微信小程序支持 `wx.getRandomValues()` 生成随机密钥
- 设备绑定防止 Token 被盗用
- 实现简单，无需后端改动

替代方案：
- 硬件安全模块 → 拒绝：小程序不支持
- 不存储，每次重新登录 → 拒绝：用户体验差

实现方式：
```
首次登录：
1. 生成设备唯一标识（openid + 设备信息 hash）
2. 生成随机 AES 密钥存储到 wx.storage
3. JWT Token 用 AES 加密后存储

后续请求：
1. 读取 AES 密钥
2. 解密 Token
3. 发送请求
```

### 3. 请求签名方案

**决策：HMAC-SHA256 签名 + timestamp + nonce**

理由：
- 防重放：nonce + timestamp 双重校验
- 防篡改：签名覆盖整个请求
- 性能好：HMAC 计算快速

替代方案：
- 非对称签名 → 拒绝：公钥分发复杂
- JWT 内嵌请求信息 → 拒绝：Token 过大会增加请求大小

实现方式：
```
小程序：
signature = HMAC_SHA256(method + url + body + timestamp + nonce, deviceSecret)
headers: X-Timestamp, X-Nonce, X-Signature

后端：
1. 验证 timestamp 在 ±5 分钟内
2. 验证 nonce 未使用（Redis 缓存）
3. 重新计算签名比对
```

### 4. 数据库敏感字段加密方案

**决策：应用层 AES-256-GCM 加密**

理由：
- 字段级加密，灵活控制
- GCM 模式提供认证加密
- KMS 托管主密钥，数据密钥由主密钥加密存储

替代方案：
- 透明数据加密 (TDE) → 拒绝：RDS Serverless 不支持
- 应用层不加密，依赖网络隔离 → 拒绝：不满足合规要求

实现方式：
```
加密：
1. 调用 KMS GenerateDataKey 获取明文数据密钥 + 密文数据密钥
2. 使用明文数据密钥 AES-GCM 加密字段
3. 存储密文数据密钥 + 密文字段 + IV + AuthTag

解密：
1. 读取密文数据密钥
2. 调用 KMS Decrypt 获取明文数据密钥
3. 使用明文数据密钥解密字段
```

### 5. LLM 数据脱敏方案

**决策：规则脱敏 + 审计日志**

理由：
- 规则脱敏简单可控
- 不依赖第三方服务
- 审计日志满足合规要求

替代方案：
- 差分隐私 → 拒绝：技术复杂度高，不适合小团队
- 联邦学习 → 拒绝：需要模型部署能力

脱敏规则：
```
姓名 → "宝宝"
出生日期 → 日龄/月龄
手机号 → 移除
地址 → 移除
体重 → 保留（非 PII）
喂养数据 → 保留（非 PII）
```

## Risks / Trade-offs

### Risk 1: KMS 调用延迟影响冷启动
→ **Mitigation**: 凭证解密后内存缓存，不每次请求都调用 KMS

### Risk 2: 数据库字段加密影响查询性能
→ **Mitigation**: 仅对 PII 字段加密，非敏感字段保持明文

### Risk 3: Token 设备绑定影响用户换设备
→ **Mitigation**: 新设备登录时提示并允许绑定新设备

### Risk 4: 请求签名增加小程序包体积
→ **Mitigation**: 使用微信内置 crypto，不引入第三方库

### Risk 5: 密钥丢失导致数据无法解密
→ **Mitigation**: KMS 密钥开启自动备份，关键密钥有手动备份

## Migration Plan

### Phase 1: 凭证管理（无业务影响）
1. 创建 KMS 密钥
2. 加密现有凭证
3. 更新 FC 环境变量
4. 部署新代码读取 KMS

### Phase 2: 数据库字段加密（需要迁移）
1. 添加加密字段（新增列存储密文）
2. 新写入数据加密存储
3. 后台任务迁移历史数据
4. 验证后删除明文字段

### Phase 3: 小程序安全增强（需要用户更新）
1. 发布新版小程序
2. 新用户使用新存储方式
3. 老用户提示重新登录

### Rollback Strategy
- KMS: 回退环境变量到明文
- 数据库: 保留明文字段备份
- 小程序: 保留旧版本兼容
